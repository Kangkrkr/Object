### **문제점 분석:**
#### 1. 단일 클래스가 모든 일을 처리
- `ShoppingApp`은 상품 추가, 가격 계산, 결제, 주문 내역 출력, 장바구니 초기화 등의 **모든 작업을 직접 처리**합니다.
- 역할을 분리하지 않아 **단일 책임 원칙(Single Responsibility Principle, SRP)**을 완전히 위반했습니다.

#### 2. 데이터가 명시적으로 드러남 (캡슐화 완전 부재)
- `productNames`와 `productPrices` 리스트를 직접 관리하고 활용함으로써 **객체 상태를 드러냄**.
- 데이터와 이를 처리하는 행위가 응집되지 않아 **추가 요구사항에 따른 변경에 취약**합니다.
    - 예: 상품 클래스(`Product`)가 없으므로 상품 관련 기능(할인, 카테고리 등)을 추가하면 큰 혼란이 발생합니다.

#### 3. 비효율적인 설계: 데이터 인덱스 의존
- `productNames`와 `productPrices`는 이름과 가격 정보를 **인덱스로 연결**하고 있으므로, 두 컬렉션이 분리될 경우 전체 데이터 정합성이 깨질 가능성이 높습니다.
- 예: 데이터를 정렬하거나 필터링하면 이름과 가격이 엉킬 수 있습니다.

#### 4. 협력 객체의 부재
- 협력 객체가 아예 없고, 모든 로직이 클래스 내부에서 해결됩니다.
- 다른 클래스로 책임을 분리하고 협력을 도모할 구조적 여지가 없으므로, 유지보수와 확장이 불가능합니다.

#### 5. 메서드가 너무 큰 책임을 가짐
- `processOrder()` 메서드는 한 메서드 내에서 **총 금액 계산, 결제, 출력, 초기화**라는 여러 행동을 처리합니다.
- 이는 **메서드 단일 책임 원칙(SRP)**을 위반했으며, 메서드 재사용성도 없습니다.

#### 6. 확장성이 전혀 없음
- 데이터를 직접 다루므로, 새로운 기능 추가나 수정(예: 다른 결제 방식 도입, 주문 내역 DB 저장 등)이 필요할 경우 기존 코드를 무조건 수정해야 합니다.
- 이런 코드는 **Open-Closed Principle(OCP) 위반**으로, 변경 가능성이 높아질수록 수정 부작용이 발생할 가능성이 큽니다.

### **정말 나쁜 설계의 여파**
#### 1. 상품 클래스의 부재
- 요구사항이 복잡해지면 (예: 상품에 카테고리나 할인 기능 추가) `ShoppingApp` 코드를 계속 수정해야 하므로 유지보수성이 떨어짐.

#### 2. 리스트로 모든 데이터를 관리
- 각 데이터가 서로 연관성을 가지므로 상품명과 가격이 일치하지 않는 에러가 발생할 가능성이 큼.

#### 3. 협력 객체 부재로 인해 전체 코드를 수정해야 함
- 결제 시스템을 변경하려면 `processOrder()`를 수정해야 하며, 데이터 관리 로직 역시 수정 대상이 되어 **전체 코드가 결합된 덩어리**가 됨.
